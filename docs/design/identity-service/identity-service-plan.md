# identity-service — plan

**Spec:** [02-IDENTITY-SERVICE.md](../../specs/project/02-IDENTITY-SERVICE.md) · RBAC background: [SPRING-PROJECT.md, "User management and RBAC"](../../specs/SPRING-PROJECT.md) · Companion: [control-api-s4-plan.md](../control-api/control-api-s4-plan.md) (decision 1: control-api was built first with test-signed tokens; this module now issues the real ones), [control-api-s4-1-jwt-validation.md](../control-api/control-api-s4-1-jwt-validation.md) (the claim contract, section 3, decision 5) · Build order: [appfleet-build-sequence.md](../appfleet-build-sequence.md). **Status: plan only, 2026-10-06; all open questions decided with the recommendations (section 5). No identity code exists beyond the skeleton.**

identity-service authenticates people and service accounts and issues the JWTs that `common-security` already validates in control-api. It owns *who you are and what you may do in general*. control-api owns *whether you may do this to this object* (spec, boundary rule). This doc covers the whole module, in steps that each get their own design doc, the way S4.1 to S4.6 did.

## 1. Starting point

What exists, and what each item costs this module:

- **A skeleton.** `identity-service/pom.xml` and `IdentityServiceApplication`. The pom already has web, actuator, JPA, Flyway, Postgres, Redis, security, `common-events`, `common-security` and **`spring-kafka`**. The `application.yml` is there too (port 8082, datasource with `currentSchema=identity`, Flyway on schema `identity`, Redis, Kafka bootstrap, `ddl-auto: validate`). `db/migration/V1__init.sql` exists but holds only comments. No controller, no entity, no table, no test. The Kafka dependency and the Kafka bootstrap setting have no use yet (open question 4).
- **The schema exists, empty.** `infra/init-schemas.sql` creates schema `identity` on the shared Postgres. Port 8082 is reserved by the spec. Nothing else in the repo reads that schema, and nothing may (spec: "no service reads another service's schema").
- **The validating side is finished, and it fixes the contract.** `common-security` validates RS256 tokens with a static public key (`appfleet.security.jwt.public-key-location`), `iss` = `appfleet.security.jwt.issuer` (for example `appfleet-identity`), `aud` contains `appfleet`, 60 s clock skew. The claims control-api reads are `sub` (user id, UUID string), `teams` (`{ "<teamId>": ["deployment:create", ...] }`), optional `perms` (global permissions, a list), plus `jti`, `iat`, `exp`. It never reads `roles`. **identity-service builds to this contract; it does not change it.** The reference implementation of the claim shape is the test helper `TestJwt` in `common-security`'s test jar.
- **A dev key pair exists for tests only**: `common-security/src/test/resources/keys/dev-private.pem` and `dev-public.pem`; control-api carries a copy of the public key and `DevKeyDriftTest` fails if the two drift. identity-service needs a private key in production; the dev one must never reach a main resource directory.
- **The permission vocabulary in use today** is `application:create`, `application:read`, `deployment:create`, `deployment:read`, `deployment:rollback` (the five in control-api's `@PreAuthorize`s). The spec adds `node:drain`, `catalog:publish`, `user:manage`. identity-service is where the full list and the role bundles are defined.
- **control-api needs nothing else from identity at runtime.** That is the spec's definition of done ("stop identity-service and control-api still authorizes") and the reason control-api was built first. This module must not add a runtime call from control-api to identity.
- **Teams exist only as a UUID.** control-api has `application.owner_team_id` and no Team table. identity-service creates the Team entity; control-api is not told about teams except through tokens.
- **No JWKS, no `kid`.** S4 plan decision 2 deferred both to this module: control-api moves from a static key to a JWKS source as a configuration change in `common-security` (step I8).
- **The web-console is a mock.** It has no login screen. A real login page is a console task after step I2, not part of this module.
- **Dev tooling quirks that apply here too** (see the control-api docs): Maven through IntelliJ's `mvn.cmd`, Postgres on host port 55432, `-Duser.timezone=UTC` for JVM runs and tests, Docker running for Testcontainers.

## 3. Decisions

1. **identity builds to the frozen claim contract and proves it with a test, not by reading.** The contract lives in S4.1 section 3, decision 5. The I2 cross-module test decodes an issued token with `common-security`'s own decoder and runs it through its authority converter. If the two modules disagree on a claim, a test fails in identity-service's build, not in a deployment.
2. **Permissions are the atoms, roles are bundles, enforcement checks permissions.** The token carries permissions per team (`teams`), never role names, as control-api expects. Roles exist for administration only. A new role is a database row, not a code change (the spec sentence to be able to say).
3. **The role hierarchy is expanded when the token is built, not stored transitively.** `role_permission` holds each role's own permissions. `RoleHierarchy` gives the roles a given role implies; the issuer takes the union of permissions of the implied roles for each team membership. Rejected: storing the closure in the database, which would need a rebuild on every change to the hierarchy.
4. **Scoped grants are the model; global roles are the degenerate case.** `team_membership(user, team, role)`. A global grant is the `perms` claim, used for platform operators only. The token must stay under about 1 KB (it travels in a header): a cap on teams per token is enforced and tested, and the measured size of a typical and a worst-case token goes into the step's doc. The cap value is open question 6.
5. **Private key from a file, never from a main resource.** `appfleet.identity.jwt.private-key-location` (a Spring `Resource`, PEM PKCS#8). A missing key fails startup. The `local` profile points at the dev key under `common-security/src/test/resources/keys` by file path; tests use the same key through the test jar. The matching public key is already in control-api's configuration.
6. **RS256 only, with a `kid` from I8.** HMAC would make every verifier a potential issuer. Before I8 the header has no `kid` and control-api uses the static key; I8 adds the `kid`, the JWKS and the overlap period.
7. **Access tokens live at most 15 minutes; refresh tokens are one-time and chained.** Rotation on every use. Reuse of a consumed token revokes the family and writes a LoginAudit row (it is a theft signal, so it is audited, not only handled).
8. **Revocation is built both ways, and the argument is written down.** The Redis denylist by `jti` (TTL = remaining life) is built in I4 because the spec asks for it. The doc then states the other side: with 15-minute access tokens and refresh rotation, the denylist narrows a window that is already short, and it costs every verifier a Redis read. Whether control-api consults the denylist at all is open question 2.
9. **Password hashing is BCrypt, cost 12, and the cost is a measured choice.** I8 records the hash time at 10, 12 and 14 on this machine. That number is the evidence for the scaling section: identity-service is CPU-bound by design and scales on a different axis from the rest.
10. **Uniform failure, in message and in timing.** An unknown user and a wrong password give the same status, body and (within noise) time, the unknown-user path hashing against a dummy hash. A test compares them. Lockout answers 423 only after the same uniform check, so the 423 itself does not reveal that an account exists (stated and tested in I5).
11. **Login audit uses `REQUIRES_NEW`,** the same pattern as control-api's `AuditEventRecorder`, so a rolled-back login still leaves its row. It is append-only: the repository has no update or delete method, and a database trigger rejects `UPDATE` and `DELETE` on the table (proved by a test that tries both with plain SQL).
12. **Deactivate, never delete.** Audit integrity. A deactivated user cannot log in or refresh; existing access tokens end by expiry (the I4 argument again).
13. **Method security is enforced and proved,** the same two ideas as control-api S4.3: permissions in `@PreAuthorize`, and a meta-test that a protected endpoint answers 403. The two deliberate bugs of I6 are kept as tests (one `@Disabled`, as the spec says).
14. **One flavour of test infrastructure.** Testcontainers Postgres and Redis through a shared abstract test base, as in control-api's `WebIntegrationTest`. Real-HTTP tests for anything that depends on the filter chain, because the base class's MockMvc does not run the security chain (found in S4.6, `DocsExposureTest`).
15. **Ids and time follow control-api:** UUIDv7 primary keys, `timestamptz`, UTC, problem-shape errors with a `correlationId`, the same `ProblemKind`-style slug list kept in one place. Whether to share the problem-shape code through `common-security` is open question 5.

## 4. What this module deliberately does not do

- **OIDC or an external identity provider** (spec: an optional profile, not required).
- **Impersonation for support flows** (spec: optional; it needs its own audit design).
- **Email verification, password reset by email, MFA.** Nothing sends email in this project yet.
- **A login page.** The web-console is a mock and gets its login screen later, against step I2.
- **Calling control-api or any other service.** Authentication centralises; authorization stays with the data (spec boundary rule).
- **Domain events for user changes** (no consumer exists; revisit with open question 4).
- **Per-endpoint rate limiting in identity.** Lockout is per account; a general limiter can reuse control-api's design later.

## 5. Open questions (all decided 2026-10-06 with the recommendations)

1. **Order.** Recommended: I1, I2, then I3 to I5, I6, I7, I8. Alternative: do I8 (JWKS) straight after I2, so control-api never depends on a static key for longer than needed. Recommendation: keep I8 last; the static key works, and rotation is easier to design once refresh and revocation exist.
2. **Does control-api consult the denylist?** Options: (a) no, access tokens end by expiry and only refresh is revoked; (b) an optional `JwtValidator` in `common-security` reads Redis, off by default, on by property. Recommendation: (b), built in I4, and off in control-api by default. The spec asks for both mechanisms and for the argument; (b) gives a real test of the cost, and the default keeps "zero extra calls on the request path".
3. **How do service accounts get a token?** Options: (a) an exchange endpoint, API key in, short-lived JWT out, so every service validates only JWTs; (b) services send the API key to every callee. Recommendation: (a). It keeps one validation path and keeps keys out of the request path of other services.
4. **Keep `spring-kafka` in identity-service's pom?** Nothing uses it. Recommendation: remove it now and add it back only if a user-changed event gets a consumer. (This is an edit to your pom, so I am asking, not doing it.)
5. **Share the problem-shape code?** control-api has `ApiExceptionHandler`, `ProblemKind` and the correlation-id filter; `common-security` already has the 401 and 403 writers. Options: (a) copy into identity-service, simple, two copies; (b) extract a small shared module. Recommendation: (a) for I1 to I3, decide again at I6 when the third and fourth handlers arrive.
6. **Cap on teams per token.** Recommendation: 20 teams, then registration of a 21st membership for a user is refused with a clear error, and the measured token size is recorded. Alternative: truncate silently (rejected: it would hide permissions). **Result of the measuring, 2026-10-06: 10** (I2 decision 8).
7. **Where the deliberate-bug tests live.** Recommendation: in identity-service's own test tree, each named after the bug (`refreshReplay_...`, `staleJwt_...`), as control-api did for the IDOR.
8. **`V1__init.sql`: leave it and start tables at `V2`, or fill it in?** Filling it is only safe if no database has applied it. Recommendation: `V2`. It costs one empty version number and cannot fail a checksum check on a database you forgot about.

### 5.1 What the decisions mean for the work

1. **Order:** I1, I2, I3 to I5, I6, I7, I8. JWKS stays last.
2. **Denylist:** built in I4 as an optional `JwtValidator` in `common-security`, reading Redis, off by default and off in control-api. A test measures its cost; the doc argues for short expiry plus rotation.
3. **Service accounts:** an exchange endpoint (API key in, short-lived JWT out) in I7. Other services validate only JWTs.
4. **`spring-kafka`:** to be removed from `identity-service/pom.xml`, together with `spring.kafka.*` in its `application.yml`. **This is an edit to your files; it is yours to make** (do it with I1). The same pom also needs `spring-boot-flyway` (Boot 4 splits Flyway auto-configuration out of the core) and, for tests, `spring-boot-testcontainers`, as control-api has. Without `spring-boot-flyway`, the migration would not run.
5. **Problem-shape code:** copied into identity-service for I1 to I3; decided again at I6.
6. **Teams per token:** the plan said 20; **changed to 10 after measuring in I2** (10 teams of ADMIN is 3098 characters, 20 is 5578; the cap keeps the worst case under 4 KB, see I2 decision 8). A user above the cap gets no token; the membership that would exceed it is refused with a clear error in I6.
7. **Deliberate-bug tests:** in identity-service's own test tree, named after the bug.
8. **Migrations:** tables start at `V2`; `V1__init.sql` stays untouched.
